Telephony and a worldwide phonebook, in one container.

Telno is the phone system and the registry in a single image: extensions, trunks, call routing, voicemail, fax, SMS, AI voice agents and an encrypted WebRTC softphone — plus the directory that answers who is this number? for six public hostnames. One database, one login, no per-seat fee and no cloud dependency.

Why Telno.

The estate audit behind this build found four applications, four logins and three design systems serving one job. Telno is the collapsed version: one control plane, one number table, one place where a change is made.

ProblemTelno answer
VoIP stack, CRM, phonebook and billing are four vendors One image — the switch, the API, the console, the registry and the ledger ship together
Per-seat and per-minute pricing Self-hosted on hardware you already own; the only bill is your carrier's
Numbers duplicated across systems E.164 is the primary key. Listings dedupe on normalized name; a submission is checked for duplicates before a human sees it
Secrets in .env, in git, in chat Provider keys live in an encrypted vault inside the container and are never returned by the API — only the last four characters are
Dunning is somebody's spreadsheet reminder A reminder ladder, a final notice, suspension and automatic reinstatement run from the ledger
Heavyweight runtime for a phone system Node 24, node:sqlite and a static UI. No SSR runtime, no ORM, no Redis, no native modules

Every surface, in one console.

Each screen is backed by the API rather than by a mock: what the console shows is what the platform actually holds.

Voice

Live and completed call history, a browser softphone, extensions with voicemail boxes, carrier trunks, call routing and IVR, AI voice agents that answer and place calls, and workflows with recorded runs.

Messages and documents

SMS, MMS and WhatsApp on your numbers; voicemail with audio and transcripts; fax in and out, accepting either an uploaded attachment or a plain-text body.

Registry and directory

The canonical number registry, a moderation queue for submitted listings, verification by email or SMS code, duplicate detection and opt-out that removes a number from every host.

Commerce

Invoices grouped by currency, payment links, a per-message delivery ledger, reminder sweeps, escalation to a final notice, suspension and reinstatement.

Estate and operations

Sites with a real device inventory — handsets and gateways belong to a site, check themselves in and go stale on their own — plus provisioning configs a device fetches to configure itself.

Platform

Health probes across every target the container can observe, connected systems, API keys with scopes, directory hostnames and the credential vault — all in Settings.

Nothing on a screen is a counter that drifts from reality: reminder counts come from the ledger, device counts from the inventory, and the newest health row is current by definition.

Encrypted because you turned it on, not because you hoped.

The generated endpoint is DTLS-SRTP and mandatory: the switch has no plain-media fallback to quietly negotiate instead.

Media

  • DTLS-SRTP on every call the browser or a device places
  • ICE and AVPF on by default; coturn with expiring, per-session credentials for carrier-grade NAT
  • Video and screen sharing in the browser, and on a device that supports it
  • Recording policy enforced by the grade of service attached to the number — never by the client

Platform

  • Passwords stored with scrypt; sessions are HMAC-signed and revocable per account
  • httpOnly, sameSite=lax cookies that are secure in production
  • Provider keys in an encrypted vault; the API returns a hint, never a value
  • CSP, frame denial and a permissions policy that opens the camera and microphone to the page and nothing else
Encryption is per leg, and that is the honest limit: your leg is encrypted the moment you use Telno, and the far end is encrypted when the far end supports it. A carrier that refuses SRTP can only be reached in the clear, which is why the console reports what a call actually negotiated rather than what was requested.

Billing that chases the invoice itself.

The ledger is the source of truth, not a counter: every rung is written before the provider is called, so a restart or a second sweep cannot send the same message twice.

The ladder

  • Reminders go out on a configurable ladder as an invoice passes its due date
  • A final notice names the day service stops — and that is the date acted on
  • Severely overdue accounts are suspended, then reinstated automatically on payment
  • Each message records the provider that carried it, or the reason it failed

Paying

  • Invoices, reminders, final notices and suspension emails carry a payment link
  • One page settles a whole balance, so a customer with three late bills needs one payment
  • Stripe webhooks mark an invoice paid against a verified signature
  • Email leaves through Resend or Mailjet, chosen in Settings, with no restart

Quick start.

  1. Start the container docker compose up -d --build — the switch, the API and the UI come up together.
  2. Read the owner password First boot prints it once in docker compose logs telno; nothing is emailed anywhere.
  3. Sign in The console is at http://localhost:8080, the public directory at /d/telno.directory.
  4. Add a number and an extension Generate the switch configuration from the console; it applies on change rather than waiting for a button.
  5. Optional demo data docker compose exec telno node src/seed.js loads listings across 19 countries, extensions and call history.
Every value that matters — session secret, API key pepper and the AMI password — is generated on first boot and kept on the data volume. Back up that volume: it holds the database, call recordings, voicemail audio and fax documents.
